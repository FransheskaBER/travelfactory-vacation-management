# Known Limitations (Draft — to be merged into README.md, Phase 7)
 
Running list of real gaps in what's built or decided, disclosed on purpose rather than hidden. Distinct from `assumptions.md`'s "Out of Scope," which covers deliberate scope exclusions — these are limitations in things that ARE being built.
 
1. **Overlap-check race condition** (ADR 0002) — the overlap check is read-then-write, not atomic. Two concurrent submissions for the same user, for overlapping dates, at nearly the same instant, could both pass the check before either commits. Not fixed here — would require a Postgres `EXCLUDE` constraint, an advisory lock, or `SERIALIZABLE` isolation (see ADR 0002's Alternatives Considered for the full comparison). This project's actual traffic level (single-user local testing) makes the window unlikely to ever surface, but it's a real gap, not a theoretical one.
2. **No dual-role / manager's-own-vacation support** — the schema gives every user exactly one exclusive role, Requester or Validator (`assumptions.md` A16). A Validator has no way to submit a vacation request for themselves — not unimplemented, structurally impossible, since no user can hold both roles at once. A real production system would need either dual-role support or a separate approval chain for a validator's own time off (approved by whom — another validator? an admin tier that doesn't exist here?). Genuine unresolved design question, out of scope for this assignment.
3. **No guard against Validator self-approval** — the assignment never specifies whether a Validator may submit their own vacation request; only Rule 6 (validators approve/reject) is stated explicitly. Nothing in the schema prevents it — `VacationRequest.user_id` accepts any `User.id`, including a Validator's own. Resolved conservatively (`assumptions.md` A16): `POST /requests` and `GET /requests/mine` are restricted to the Requester role. This is a scope choice, not a technical limitation — `assertPending()` only checks `status`, never whether `reviewer !== requester`, so opening these endpoints to Validators would allow a Validator to approve their own request with no guard against the conflict of interest. Building that guard is real, untested work the assignment doesn't ask for.
4. **No token revocation or refresh** (D12) — a stolen token stays valid until expiry (24h); there is no server-side session state to invalidate it against. Production version would use short-lived access tokens with rotated, DB-backed refresh tokens.
5. **~~JWT in localStorage is XSS-readable~~ — resolved by the httpOnly-cookie migration** (docs/specs/12-cookie-transport.md). The token now travels only in an `HttpOnly` cookie, unreadable by any script, closing the XSS token-theft channel this entry described (it previously compounded limitation 4/D12 — a stolen 24 h token with no revocation). The store persists only `{ role, userId, expiresAt }`, which are not secrets: tampering yields UI drift only, the backend's `requireRole` is still the enforcement. The trade this bought is entry 7 (CSRF surface); the migration also purges the stale 4.8-era `token` key from existing browsers' localStorage on first load.
6. **Authenticated header shows no user identity** (spec 4.8 §2) — the JWT carries only `userId`/`role` and no `/me` endpoint exists, so the logged-in header has no name or email to display.
7. **CSRF stance: `SameSite=Lax` only** — cookies auto-attach to requests, so cross-site request forgery becomes possible in principle where localStorage-header auth was structurally immune. Mitigation: `SameSite=Lax` blocks the cookie on cross-site POSTs, and every mutating endpoint in this API is a POST — adequate for this app's threat model. Production hardening (per-request CSRF tokens or `SameSite=Strict`) is documented here, not built.
8. **Dev transport requires the Vite proxy; production must be same-origin or gateway-configured** — credentialed requests forbid `Access-Control-Allow-Origin: *`, and CEF's dev server hardcodes exactly that in its preflight handler (not configurable). The mandatory `server.proxy` in `vite.config.ts` makes dev API calls same-origin, so CORS never applies locally; a production deployment must either serve frontend and API from one origin or configure real CORS with credentials at the gateway. Side effect: 4.8's `FRONT_END_URL` import-time limitation is superseded-as-moot locally (still effective on deployed Lambda).
9. **`Set-Cookie` placement on real API Gateway v2** — locally the CEF dev server writes response headers verbatim, so the cookie flows; on actual API Gateway v2 a Lambda result's cookies belong in the `cookies` array, not `headers`. This only bites on AWS deployment — one-line fix there, not built here.
10. **Team view: a cross-month vacation appears only under its start month** (spec 4.9 §8 Q2) — the shared view groups by the month of `startDate`, so an Aug 30–Sep 3 vacation sits under August only; someone scanning the September header misses it, and the row's full date range is the only cross-month signal. Deliberate trade against the span-splitting/duplication complexity A14 already declined with the calendar grid — but it does cut against US-4's stated purpose (planning around teammates), which is why it's disclosed here rather than treated as obviously free.
