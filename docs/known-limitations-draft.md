# Known Limitations (Draft — to be merged into README.md, Phase 7)
 
Running list of real gaps in what's built or decided, disclosed on purpose rather than hidden. Distinct from `assumptions.md`'s "Out of Scope," which covers deliberate scope exclusions — these are limitations in things that ARE being built.
 
1. **Overlap-check race condition** (ADR 0002) — the overlap check is read-then-write, not atomic. Two concurrent submissions for the same user, for overlapping dates, at nearly the same instant, could both pass the check before either commits. Not fixed here — would require a Postgres `EXCLUDE` constraint, an advisory lock, or `SERIALIZABLE` isolation (see ADR 0002's Alternatives Considered for the full comparison). This project's actual traffic level (single-user local testing) makes the window unlikely to ever surface, but it's a real gap, not a theoretical one.
2. **No dual-role / manager's-own-vacation support** — the schema gives every user exactly one exclusive role, Requester or Validator (`assumptions.md` A16). A Validator has no way to submit a vacation request for themselves — not unimplemented, structurally impossible, since no user can hold both roles at once. A real production system would need either dual-role support or a separate approval chain for a validator's own time off (approved by whom — another validator? an admin tier that doesn't exist here?). Genuine unresolved design question, out of scope for this assignment.
3. **No guard against Validator self-approval** — the assignment never specifies whether a Validator may submit their own vacation request; only Rule 6 (validators approve/reject) is stated explicitly. Nothing in the schema prevents it — `VacationRequest.user_id` accepts any `User.id`, including a Validator's own. Resolved conservatively (`assumptions.md` A16): `POST /requests` and `GET /requests/mine` are restricted to the Requester role. This is a scope choice, not a technical limitation — `assertPending()` only checks `status`, never whether `reviewer !== requester`, so opening these endpoints to Validators would allow a Validator to approve their own request with no guard against the conflict of interest. Building that guard is real, untested work the assignment doesn't ask for.
4. **No token revocation or refresh** (D12) — a stolen token stays valid until expiry (24h); there is no server-side session state to invalidate it against. Production version would use short-lived access tokens with rotated, DB-backed refresh tokens.
